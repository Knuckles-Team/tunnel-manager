# CONN-TUNNEL-MANAGER-INVENTORY requirements

Every requirement this specification owns, with the proof that closes it. Delivery state and
public evidence for each ID are recorded in [`status.json`](status.json); this file defines what
each ID means. The design is in [`spec.md`](spec.md) and [`plan.md`](plan.md), the test contract
in [`test-spec.md`](test-spec.md), and the work order in [`tasks.md`](tasks.md).

| ID | Requirement | Verification |
|---|---|---|
| `CONN-TUNNEL-MANAGER-INVENTORY-R001` | **One canonical host inventory path across surfaces.** tunnel-manager resolves the shared host inventory from exactly one path, `$XDG_CONFIG_HOME/scion-sdk/inventory.yml` (using the XDG platform default when unset), with no working-directory, packaged-resource, legacy `.yaml`, or per-service fallback, and every CLI, library, MCP, and container surface reads that same file. Caller chain: every surface (CLI, library, MCP tools, container) calls `default_inventory_path` (tunnel_manager/tunnel_manager.py:388) to find the inventory file. Shape: `default_inventory_path` in `tunnel_manager/tunnel_manager.py` returns the single path `$XDG_CONFIG_HOME/scion-sdk/inventory.yml` and drops the `agent-connectors` directory and the legacy `.yaml` fallback; the container mounts that file read-only. Proving test: `tests/test_inventory_path.py::test_single_canonical_inventory_path`. Proving test: `tests/test_inventory_path.py::test_single_canonical_inventory_path`. | A fixture with only the canonical file present confirms every automatic reader resolves it, while a container-mount test confirms the deployed container reads the identical file read-only. |
| `CONN-TUNNEL-MANAGER-INVENTORY-R002` | **Fleet name.** `pyproject.toml` declares `tunnel-manager-mcp` as the single `scion_sdk.connector` entry point. The content pack, the manifest `connector`, the fingerprints and the ingest binding all carry `tunnel-manager-mcp`. Caller chain: `tunnel-manager` in `pyproject.toml` runs `tunnel_manager.tunnel_manager:main`, which builds the server from the `scion_sdk.connector` entry point `tunnel_manager:connector` (`tunnel_manager/__init__.py:129`); `connector_name("tunnel_manager")` in the SDK resolves the same entry point name for the content pack, the manifest and the ingest binding. Shape: `pyproject.toml` entry point `tunnel-manager-mcp`, the `connector_name` helper of the SDK and the `ConnectorContent`/`IngestBinding` calls under `tunnel_manager/`; reuses the SDK name resolution and adds no second constant. Proving test: `tests/test_fleet_name.py::test_connector_name_is_the_fleet_name`. | Every connector name in the package is `tunnel-manager-mcp`. |
| `CONN-TUNNEL-MANAGER-INVENTORY-R003` | **SSH runs without a local username.** Every SSH connection uses the inventory entry's `user` explicitly and never depends on the local process username, so a container uid with no passwd entry and no `USER`/`LOGNAME` still connects. Tool failures are logged with their cause. The published image creates the runtime uid as a real user with a home directory. Caller chain: an MCP tool of `tunnel_manager/mcp_server.py` builds a `Tunnel` from the inventory entry (`tunnel_manager/mcp_server.py:397`), whose `user` is passed to paramiko explicitly. Shape: `Tunnel` in `tunnel_manager/tunnel_manager.py` resolves the username from the inventory entry and never calls `getpass.getuser` first; tool failures log their cause. Proving test: `tests/test_no_local_username.py::test_tunnel_uses_explicit_user_without_local_username`. | With `getpass.getuser` raising `OSError`, a `Tunnel` built from an inventory entry resolves its username, and a failing tool call logs the underlying exception. |
